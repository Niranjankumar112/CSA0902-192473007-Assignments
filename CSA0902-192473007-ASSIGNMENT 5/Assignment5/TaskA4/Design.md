# A4 – What Should Be Serialized? (4 marks)
Mark the live JDBC `Connection` as `transient`; it is a runtime resource, not durable state, and usually is not serializable. Password should not be serialized: omit it from persisted state or mark it transient and store credentials securely elsewhere. Ordinary persistent fields such as room/resident names and register numbers may be serialized if policy permits. The full reachable object graph is traversed; referenced serializable objects are written, preserving shared references/cycles. Any non-transient reachable non-serializable object can cause `NotSerializableException`.

Declare an explicit `serialVersionUID`. When a compatible class adds a field, older streams normally deserialize with the new field set to its default value (for example null or 0). If the class UID is incompatible, `InvalidClassException` is thrown. Explicit UID helps control compatibility but does not automatically migrate/validate data.

CSV/JSON are language-independent and human-readable, usually easier to evolve with optional fields and schema versions. Java serialization is convenient for Java object graphs but couples files to Java class definitions and requires careful security/version management. Save/load of n residents is O(n) time for either; serialized size may be compact but includes class metadata, while text size depends on field representation.
